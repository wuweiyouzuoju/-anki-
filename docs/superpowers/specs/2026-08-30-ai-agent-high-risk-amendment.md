## 1. 范围变更

原设计把删除、笔记类型迁移、模板/CSS 修改留到第二阶段。用户现要求与普通制卡/改卡一并完成。本增补只改变交付顺序，不放宽安全边界：Agent 仍是 ArkTS 层，不能调用裸 RPC、数据库、文件系统、Shell，也不修改 Anki Rust 源码或 protobuf。

## 2. 高风险工具

- `propose_delete_notes`：按稳定 note ID 提出删除笔记草稿，并用 `CardsOfNote` 计算实际删除卡片数。
- `propose_delete_cards`：按稳定 card ID 提出删除草稿；执行前重新读取卡片并显示其 note ID。
- `propose_change_note_type`：使用后端变更信息生成字段/模板映射草稿；不得由模型直接提供 RPC JSON。
- `propose_update_note_type_templates`：针对一个笔记类型生成模板/CSS 前后差异；执行前重新读取完整旧版 JSON。
- `propose_delete_deck`：显示牌组树路径和后端计算的受影响卡片数；不允许删除未在本轮读取结果中的牌组。
- `propose_delete_note_type`：显示名称、使用笔记数和实际卡片数；不允许删除当前上下文之外的类型。

所有工具只产生 `ChangeDraft`，不会在 Agent 工具循环内提交。

## 3. 两阶段确认

第一阶段展示逐项 diff、对象名称、稳定 ID、笔记数和实际卡片数，用户可编辑选择范围。确认后应用重新读取所有对象并做基线冲突检测。第二阶段使用独立不可逆确认页，明确显示最终数量；只有用户再次点击“确认执行永久操作”才调用现有 Service。页面退出、网络取消、模型继续输出都不能触发提交。

结构修改与删除不能和普通写操作混在同一次提交中。每个高风险草稿具有唯一 ID；已成功或已冲突的草稿不能重复执行。批量仍按实际卡片数默认 100、最高 1000 分批，删除牌组/笔记类型不自动拆成多个语义操作。

## 4. 执行与恢复

- 普通字段、标签和移动牌组继续进入 Anki 撤销栈。
- 删除和结构修改使用现有 Anki Service；应用不伪造事务能力。批次成功即保留，失败项保留并显示原因。
- 模板/类型变更提交前导出基线 JSON 到应用私有内存中的会话记录，不写公共文件；失败时给出可重试草稿，不自动反向写回。
- 每次提交保存脱敏审计：草稿 ID、工具名、对象 ID、数量、时间和结果；不保存 API 密钥、原始推理或媒体二进制。

## 5. 验收

- 模型无法绕过二次确认或直接触发任何高风险 Service。
- 入口上下文之外的 ID、冲突基线、重复草稿、超过 1000 的单批请求全部被拒绝或拆批。
- 删除/模板/类型迁移均显示准确的实际卡片影响，不用模板数猜测。
- 测试证明页面加载与模型输出结束都不会提交；只有第二次用户确认事件能调用执行器。
- 全量测试、HAP 构建和实体设备验证通过后才称为完成。
