# 3.0.0 Agent 工具契约与全量可观测性设计

> 归档状态：这是一次性历史设计/执行记录，不是当前路线图、待办列表或操作手册。未勾选项不表示仍未实现；当前事实请查阅 [文档导航](../../README.md)、[开发状态](../../DEVELOPMENT_PLAN.md)、[当前架构](../../architecture.md) 和实际源码/测试。


日期：2026-08-31

## 目标

本次精进解决的不是“让模型多试几次”，而是让模型、Runner、工具校验器和界面共同遵守一份可验证的工具契约：模型在调用前获得完整 Schema、标准参数模板、禁止规则和当前笔记类型的真实字段；调用失败后获得精确到字段路径的机器可读错误；用户可以默认展开查看每一次工具调用的输入、输出和失败原因。

完成后，应直接消除当前 `propose_create_notes` 反复把 `reason` 放进 `notes[]` 的无效循环，并使类似结构错误在第一次失败后即可被模型定向修正。若模型仍原样重复同一失败，Runner 应提前终止，而不是耗尽全部安全轮次。

## 范围与非目标

本次包含：

1. 统一的工具 Schema、参考模板和禁止规则。
2. 精确的结构化工具参数错误。
3. 全部工具调用默认展开显示，包括成功和失败。
4. 工具调用输入、结果和错误的脱敏、截断及历史恢复。
5. 重复失败识别与提前熔断。
6. 对“年份作为填空”等可确定要求的结果约束。

本次不包含：

1. 不修改 Anki Rust 源码、protobuf、NAPI ABI 或数据库 schema。
2. 不让模型绕过 `ChangeDraft`、确认令牌或 `AgentDraftExecutor` 直接写库。
3. 不用正则假装判断“内容是否属于中国现代史”等开放语义；这仍主要取决于模型与可靠资料。
4. 不增加第二个模型充当语义裁判。
5. 不开放任意代码执行、任意 HTTP 请求或对媒体二进制的无条件发送。
6. 不依赖 DeepSeek 当前 Responses 协议未明确支持的 `strict` 参数。

## 现有失败的责任划分

截图中的失败由 Agent 契约层和模型共同造成，但当前首先应修 Agent：

- 模型生成了非法参数：把仅允许出现在顶层的 `reason` 放进了 `notes[0]`。
- 现有 Schema 实际已经禁止该字段，但模型看到的提示缺少足够直观、统一的标准模板。
- 校验器只返回通用 `invalid_tool_arguments`，Runner 再把它压缩成 `{\"tool_error\":\"invalid_tool_arguments\"}`；模型不知道具体错在 `notes[0].reason`，于是连续重复。
- 界面只显示“开始/失败：propose_create_notes”，用户看不到参数、错误路径、允许字段或校正模板。

因此，不能把连续七次失败简单归为“模型不行”。开放知识内容可能是模型质量问题；确定性的 JSON 结构失败应由 Agent 契约、校验和纠错链路兜底。

## 单一工具契约

### 唯一来源

每个工具在 `AgentToolCatalog` 中只维护一份契约元数据：

- JSON Schema；
- 标准参数模板；
- 禁止规则；
- 简洁用途说明；
- 是否为读工具、草稿工具或高风险草稿工具。

Provider 请求、运行时校验、错误中的 `validTemplate` 和契约测试都从这份目录生成或引用，避免提示词、Schema、校验器和界面各写一套互相漂移的格式。

### `propose_create_notes` 标准契约

模型获得的模板应等价于：

```json
{
  "targetDeckId": "<目标牌组 ID>",
  "targetNotetypeId": "<目标笔记类型 ID>",
  "notes": [
    {
      "fields": ["<字段 1>", "<字段 2>"]
    }
  ],
  "reason": "<整批草稿的简短理由，可省略>"
}
```

必须同步明确：

- `reason` 只能是顶层字段，不能出现在 `notes[]` 中；
- `notes[]` 的每一项只能包含 `fields`；
- `fields` 必须按当前笔记类型的真实字段顺序提供，数量必须一致；
- 填空笔记的合法 cloze 字段必须包含 `{{c1::答案}}` 等结构；
- 用户明确数量时，`notes.length` 必须恰好等于该数量；
- 不得自行发明牌组 ID、笔记类型 ID、字段或工具参数。

Runner 在每轮提示中追加当前目标的真实上下文示例，例如字段名、字段数量、cloze 字段序号和用户明确数量。通用模板不硬编码某个牌组或笔记类型。

### Provider 适配

`ProviderProtocol` 继续把 JSON Schema 作为函数工具参数发送；同时把标准模板和禁止规则加入工具描述，使不完全遵循 Schema 的模型也得到直观参考。

不把“开启 strict 模式”作为成功前提。DeepSeek 的 strict 工具模式文档针对 `/beta` Chat Completions，而当前应用使用 Responses 续传协议；在官方 Responses 契约未明确支持前，不发送未经确认的字段。

## 精确结构化错误

### 错误数据

工具参数校验失败统一产生结构化诊断：

```json
{
  "code": "unexpected_property",
  "path": "notes[0].reason",
  "receivedKeys": ["fields", "reason"],
  "allowedKeys": ["fields"],
  "message": "reason is only allowed at the top level",
  "validTemplate": {
    "targetDeckId": "<deck-id>",
    "targetNotetypeId": "<notetype-id>",
    "notes": [{ "fields": ["<field-1>", "<field-2>"] }],
    "reason": "<batch reason>"
  }
}
```

诊断至少覆盖：

- 缺失必填字段；
- 多余字段；
- 类型错误；
- 数组元素路径；
- 字段数量不符；
- cloze 标记缺失或出现在不允许的字段；
- 明确张数不符；
- 明确要求年份填空但 cloze 答案不满足年份约束。

### 返回给模型

Runner 不再只返回通用错误码，而是把净化后的结构化诊断作为 `function_call_output` 返回。模型能够直接读取错误路径、允许字段和合法模板并重提。

第二次出现相同工具、相同净化参数及相同诊断时，Runner 在诊断中加入强制纠错指令，明确要求基于 `validTemplate` 重建参数，不允许原样重试。第三次仍完全相同则以 `agent_repeated_tool_failure` 提前结束，并向用户显示最后一次诊断，不再浪费剩余安全轮次。

“相同失败”按稳定规范化后的工具名、参数和诊断指纹判断；对象键顺序差异不构成新尝试。

## 工具过程全量显示

### 默认展开

工具过程不再是若干状态字符串，而是类型化的审计条目。每一次调用都默认展开，不区分成功或失败，按真实发生顺序展示：

- Provider 轮次与本轮工具序号；
- 工具名称；
- 状态：开始、成功或失败；
- 净化后的完整参数；
- 成功结果或结果摘要；
- 失败错误码、精确路径、实际字段、允许字段、说明与合法模板；
- 是否属于重复失败、当前重复次数和熔断原因；
- 对草稿类工具，显示拟议动作数量和影响范围摘要，但不把“产生草稿”描述为“已经写入”。

界面允许用户手动收起单条记录，但新记录默认展开。思考过程、正文回答和工具过程继续分区显示，不能把模型正文伪装成工具结果。

### 隐私与大小限制

“全部显示”指显示全部安全的工具审计内容，不包括敏感凭据或大体积二进制：

- 键名匹配 `apiKey`、`authorization`、`bearer`、`token`、`secret` 等一律显示为 `[REDACTED]`；
- 不保存或显示请求头中的认证信息；
- `data:` 媒体、图片/音频字节和超长内容显示类型、长度与截断标记；
- 单个字段、单条工具记录和单会话审计总量均设置确定上限；
- 截断必须明确显示 `truncated=true`，不能静默丢失；
- 不保存 Provider 未公开的隐藏推理。

参数和输出在进入 UI、日志或持久化前共用同一个递归净化器，不能只在某一层脱敏。

## 历史恢复

会话历史保存净化、截断后的类型化工具审计条目。恢复历史后，用户仍能看到当时每个工具的参数、结果、错误路径和模板；草稿确认令牌、API key、媒体字节与隐藏推理不恢复。

读取旧版仅含字符串数组的历史时必须兼容：将旧字符串转成“旧版摘要”条目，不因 schema 升级丢失整个会话。新字段均应有安全默认值。

## 可确定任务约束

### 明确数量

沿用现有明确数量解析。若用户要求 5 张，最终可接受草稿必须恰好包含 5 条合法笔记；数量不符的草稿不登记。

### 年份作为填空

当用户明确表达“年份是填空部分”“考察年份”等等价意图，生成结果增加确定性校验：

- 用户要求的每一张卡都必须至少包含一个合理的四位年份 cloze 答案；
- 不判断历史事件陈述本身是否语义正确；如使用联网搜索，事实来源仍由现有来源机制展示。

此约束只在用户明确要求时激活，不把所有数字题误判成年份题。

## 数据流

1. 页面生成用户请求及当前目标上下文。
2. `AgentRunner` 从 `AgentToolCatalog` 取得 Schema、模板和规则，交给 `ProviderProtocol`。
3. Provider 返回工具调用。
4. Runner 立即产生“开始”审计条目；参数先净化后交给 UI，原始参数仅在内存中进入校验器。
5. Schema/语义校验通过后调用 `AgentToolRegistry`；失败则生成结构化诊断。
6. 成功输出或结构化错误均先净化、截断，再同时交给 Provider 续传、UI 与历史存储。
7. 草稿工具只有在全部约束通过后才登记 `ChangeDraft`；真正写入仍需用户确认并经过现有执行边界。
8. Runner 检查重复失败指纹、轮次和工具次数上限，决定继续、强制纠错或提前终止。

## 测试与验收

实现采用测试驱动，至少包含以下自动化契约：

1. 目录中的每个标准模板均能通过其 Schema 和运行时解码。
2. `propose_create_notes` 的顶层 `reason` 合法，`notes[0].reason` 精确报 `unexpected_property` 与路径。
3. 错误回传包含 `allowedKeys` 和可通过校验的 `validTemplate`。
4. 对象键顺序不同的同一失败得到相同指纹；第三次相同失败提前终止。
5. 不同参数或不同路径的失败不被误判为重复失败。
6. 成功和失败工具调用均产生默认展开的类型化条目，参数与输出可见。
7. key、authorization、token、data URL 与超长字段在 UI/历史前被脱敏或截断。
8. 新历史可完整恢复工具详情，旧字符串历史可兼容读取。
9. “5 张、年份作为填空”只接受恰好 5 张且每张符合年份 cloze 约束的草稿。
10. 普通填空或包含非年份数字的请求不会被年份约束误伤。
11. 现有普通笔记、填空笔记、导入自定义笔记类型、AI 改卡、高风险确认与部分失败重试测试保持通过。

最终验证包括：

- 新增聚焦测试先红后绿；
- 相关模块测试；
- 完整 `npm test`；
- 完整 `npm run build:app`；
- 使用 `hdc install -r` 覆盖安装可用设备；
- 在 AI 制卡页实际触发一次成功工具调用和一次受控失败，确认二者均默认展开且详情完整脱敏；
- 再次验证 5 张中国现代史年份填空请求能生成恰好 5 张合法草稿。

## 决策记录

1. 选择 Schema 驱动的完整工具契约，不采用仅增强提示词的轻量补丁。
2. 全部工具调用均显示，成功与失败一视同仁。
3. 所有工具详情默认展开，用户可手动收起。
4. 仍保留脱敏、截断和媒体隔离；“全部显示”不等于泄露密钥或二进制。
5. 第三次完全相同的工具失败提前熔断。
6. 对年份填空等确定要求做程序校验，对开放语义正确性不做伪确定判断。
7. 不改 Anki 后端 ABI/数据库，只精进 ArkTS Agent 契约、Runner、审计 UI 与持久化。
